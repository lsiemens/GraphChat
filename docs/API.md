# API Interface
This listed interface is provisional and may not match the implemented interfaces.
The base URL is `/api/v1`, e.g. `http://localhost:8000/api/v1`.

## Endpoint Summary
The endpoints for the API are as follows. The endpoint variables are:

- `graph_id`: The ID of a graph. Currently always set to "0", in the future this is expected to be a UUID.
- `node_id`: The ID of a node in a graph. The ID is a SHA-256 hash of its contents and is generated by the Python server.

By design, `node_id` (or `NodeID` in JSON) is highly sensitive to the data
included and the exact serialization used when generating the hash. While it is
possible to reproduce `NodeID`s for validation, the Python server should be
treated as the single authoritative source for `node_id`.

### Graphs
Optional for the future, allowing more than one graph that can be switched by
the user. For now, `graph_id` is fixed to "0".

- GET  `/graphs` : List all available graphs
- POST `/graphs` : Create new graph
- GET  `/graphs/{graph_id}` : Get metadata (title, description, ...)

### Nodes
The core of the API, providing creation and retrieval of elements of the directed
acyclic graph (DAG). Nodes in the graph are immutable and so can not be modified,
but a delete operation may be added later. To preserve the DAG, deleting a node
must also delete **all traversable downstream nodes**.

- POST `/graphs/{graph_id}/nodes` : Create a new node using a prompt
- GET  `/graphs/{graph_id}/nodes` : List the node IDs in the graph
- GET  `/graphs/{graph_id}/nodes/{node_id}` : Get a given node

### View
A prompt's context is represented by a topological ordering of the traversable
(upstream-only) subgraph, i.e. a projection of the upstream subgraph. A view is
one such projection that provides the exact linear ordering of messages to be
supplied as the LLM's context.

The server acts as a repository of algorithms for generating views of the graph.

- GET  `/graphs/{graph_id}/views` : List the available methods for generating views
- POST `/graphs/{graph_id}/views/{view_name}` : Generate a view of the traversable subgraph

Note the {view_name} should be a lowercase human readable name, with spaces
replaced by '_'.

### General
Endpoints for retrieving properties, configuration, and statistics.

- GET `/system/models` : Get available LLM models
- GET `/graphs/{graph_id}/stats` : Get graph wide usage and statistics (total cost, tokens)
- GET `/graphs/{graph_id}/nodes/{node_id}/info` : Get metadata for the node (tokens used, ...)

## JSON
This section outlines the formatting of requests and responses. The JSON
definitions below use a JSON-Schema-like notation for describing request and
response structures. They are for illustration only and not intended to be a
JSON Schema.

### Common Specifications
The following common objects and types are used throughout the API.

The ID of a node, corresponding to `node_id` in the endpoints. It consists of
the hexadecimal digits of the SHA-256 hash of the relevant node's contents.

```
{
  "title": "NodeID",
  "description": "ID for a node, hexadecimal digits of a SHA-256 hash of the node's contents",
  "type": "string",
  "additionalProperties": false,
}
```

The specification for a node in the graph. A node records the user's request,
the generated reply, the model used, and its upstream dependencies. Provided
that all `upstream` nodes must already exist the result is a DAG.

```
{
  "title": "Node",
  "type": "object",
  "properties": {
    "id": {
      "type": "NodeID" },
    "upstream": {
      "type": "array",
      "description": "A list of the IDs of the upstream nodes",
      "items": {
        "type": "NodeID" }},
    "context": {
      "type": "array",
      "description": "A list of the IDs of the context as presented to the LLM",
      "items": {
        "type": "NodeID" }},
    "request": {
      "type": "string",
      "description": "The user's prompt" },
    "reply": {
      "type": "string",
      "description": "The agent's reply" },
    "model": {
      "type": "string",
      "description": "The LLM model used to generate the agent's reply" },
    "costUSD": {
      "oneOf": [{
        "type": "number" }, {
        "type": "null" }]}},
  "additionalProperties": false,
}
```

### Nodes

#### Create Node

Send the following JSON using `POST` to `/graphs/{graph_id}/nodes`. The server
generates the node's reply and ID.

```
{
  "title": "Create Node",
  "type": "object",
  "properties": {
    "model": {
      "type": "string",
      "description": "The LLM model to use when generating the agent's reply" },
    "upstream": {
      "type": "array",
      "description": "A list of the IDs of existing upstream nodes",
      "items": {
        "type": "NodeID" }},
    "context": {
      "type": "array",
      "description": "A list of the IDs defining the context for the prompt",
      "items": {
        "type": "NodeID" }},
    "timestamp": {
      "type": "string",
      "description": "An ISO date string" },
    "content": {
      "type": "string",
      "description": "The prompt for the LLM" }},
  "additionalProperties": false,
}
```

The expected response is the newly created node.

```
{
  "title": "Created Node",
  "description": "The node created in the server",
  "type": "Node",
  "additionalProperties": false,
}
```

#### List Node IDs

Send a `GET` request to `/graphs/{graph_id}/nodes`. The response contains the
IDs of all nodes belonging to the graph.

```
{
  "title": "List Node IDs",
  "type": "object",
  "properties": {
    "ids": {
      "type": "array",
      "description": "A list of all of the NodeIDs in the graph",
      "items": {
        "type": "NodeID" }}},
  "additionalProperties": false,
}
```

#### Get Node

Send a `GET` request to `/graphs/{graph_id}/nodes/{node_id}` to retrieve a
specific node.

```
{
  "title": "Created Node",
  "description": "The node retrieved from the server",
  "type": "Node",
  "additionalProperties": false,
}
```

The `node_id` in the request should match the `Node.id` in the response.

### Views

#### List View methods

Send a `GET` request to `/graphs/{graph_id}/views`. The response contains the
view name of all available view methods. Note the graph_id is irrelevant in
this case.

```
{
  "title": "List View names",
  "type": "object",
  "properties": {
    "viewNames": {
      "type": "array",
      "description": "A list of all of the available view methods",
      "items": {
        "type": "string" }}},
  "additionalProperties": false,
}
```

#### Compute View

Send the following JSON using `POST` to `/graphs/{graph_id}/views/{view_name}`.
The server computes the view using the provided method.

```
{
  "title": "View upstream",
  "type": "object",
  "properties": {
    "upstream": {
      "type": "array",
      "description": "A list of the IDs of existing upstream nodes",
      "items": {
        "type": "NodeID" }},
  "additionalProperties": false,
}
```

The expected response is the following JSON defining the context found for the
given view method and upstream nodes.

```
{
  "title": "View context",
  "type": "object",
  "properties": {
    "context": {
      "type": "array",
      "description": "A list of the IDs defining the context for the prompt",
      "items": {
        "type": "NodeID" }},
  "additionalProperties": false,
}
```
